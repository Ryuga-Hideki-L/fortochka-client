## Подтверждённые факты (verified)

1. **TSPU «заморозка» по датацентру (июнь 2025).** TCP-соединения к «подозрительным» иностранным
   ДЦ-IP замораживаются после ~15–20 КБ ответа сервера (особенно на мобильных сетях), даже если
   трафик выглядит как обычный HTTPS или VLESS/Reality поверх TLS 1.3. Явно названы **OVH, Oracle,
   Cloudflare, Hetzner, DigitalOcean, AWS**. → Прямо объясняет, почему наш прямой OVH-IP и Gcore-edge душат. [3-0]
   _fbk.info/files/acf-internet-report-EN.pdf_

2. **Что деградировало / что живёт (2026).** OpenVPN, WireGuard(ванильный), Shadowsocks, Trojan,
   IKEv2/IPsec — сильно порезаны/заблокированы. Устойчивее — камуфляжные: **VLESS/XRay (TLS+WS+CDN),
   AmneziaWG, NaiveProxy, Hysteria** при правильной настройке. Но всё это «движущаяся мишень, не
   постоянное решение». [3-0]

3. **Самый устойчивый паттерн доставки (проверен на Умном Голосовании Навального):** подписанный JSON
   конфиг + ротация эндпоинтов с низким TTL + резолв через DNS-over-HTTPS + SNI-faking + упреждающая
   ротация по пулу заранее зарегистрированных доменов и нескольких CDN (**Bunny, Fastly, Amazon
   CloudFront**). Клиент узнаёт свежие адреса бэкенда БЕЗ нового релиза приложения при каждом блоке. [3-0]

4. **ТСПУ анализирует поведение, а не содержимое (июнь 2026):** TLS-фингерпринты, число параллельных
   соединений, подсети назначения — сигнатурная маскировка не спасает. [2-1]

5. **VLESS+Reality: «Connected», но данные не идут** — массовый failure с февраля 2026, усилился в июне 2026. [3-0]

6. **«Неблокируемых протоколов больше нет»** — скорость адаптации инфраструктуры важнее выбора протокола. [3-0]

7. **Блок Cloudflare — эскалирующая кампания против иностранных CDN** («пробный выстрел» по словам
   техдира Роскомсвободы, чтобы согнать ресурсы с Cloudflare). Сигнал: троттлинг CDN будет нарастать. [3-0]

8. **VLESS заблокирован в конце 2025** (по сообщениям) — бьёт прямо по нашей опоре на VLESS+Reality и VLESS+WS+TLS. [3-0]

9. **Мануал по детекту VPN:** сравнение поведения через параллельные запросы к российскому и
   иностранному домену — активное зондирование, а не статический фингерпринт. [3-0]

10. **ТСПУ DPI читает трафик в реальном времени**, определяет тип трафика (не только назначение),
    может троттлить на любой % или блокировать. [3-0]

### Опровергнуто
- «Cloudflare намеренно заблокировали 19.03.2025 из-за обхода» — [1-2], т.е. сомнительно как формулировка.

### Дополнительно подтверждено (прямой fetch habr.com/ru/articles/1047442, 2026-07-22)
- **Трёхсигнальная AND-логика заморозки:** (1) ASN/подсеть иностранного ДЦ [Hetzner/DO/**OVH**], с конца
  мая 2026 + ряд РФ-облаков; (2) подозрительный TLS-fingerprint (Chrome/Safari uTLS в «плохой» подсети);
  (3) **>3 параллельных TLS к одному SNI** с малой задержкой → фриз ~120с. Блок только при совпадении ВСЕХ трёх.
- **Фриз на стадии TLS-хендшейка / сразу после:** «Finished» и Application Data дропаются на ТСПУ БЕЗ
  RST/FIN (blackholing). Клиент видит i/o timeout через 10–30с. → объясняет «Connected, данных нет».
- **Почему TCP/Vision палится:** одно TCP = один поток; несколько вкладок = несколько TCP+TLS к одному
  SNI → прямой триггер Сигнала 3. **gRPC/xHTTP:** один долгоживущий h2-канал с мультиплексом до ~100
  streams → нет залпа хендшейков. **Hysteria2/QUIC:** UDP, механизм параллельных TCP к нему неприменим.

### СДЕЛАННЫЙ ФИКС (клиент, config.go)
- Из auto-пула (urltest) исключён сырой **tcp/Vision** транспорт, когда есть устойчивый (grpc/ws/http).
  Причина: крошечный пробник `generate_204` ПРОХОДИТ на tcp/Vision, а реальный трафик замерзает после
  15–20 КБ → urltest залипал на мёртвом транспорте. tcp остаётся в selector'е как ручной/последний резерв.
- **Следующий большой шаг (не сделано):** доставка AmneziaWG (UDP 51833) в клиент — единственный транспорт
  категорически вне TCP-фриза. Требует per-user AWG-конфига в подписке/клиенте.

## План под наш сетап на 10 человек (по фактам выше)

**Ключевой вывод:** нас душат не по протоколу, а по **репутации IP (OVH-ДЦ)** + **поведению**
(параллельные TLS, объём ответа). Значит чинить надо транспорт-разнообразие, происхождение трафика и доставку.

### Приоритет 1 — дёшево, высокий эффект
1. **AmneziaWG (UDP 51833) сделать основным, не запасным.** UDP обходит TCP-заморозку по объёму
   ответа (факт 1 — про TCP). Уже развёрнут — поднять в клиенте в топ selector/urltest.
2. **Убрать зависимость от одного CDN-хоста подписки.** Реализовать паттерн из факта 3: клиент носит
   встроенный пул из 2–3 источников конфига (Gcore + Bunny/Fastly/CloudFront), резолв через DoH,
   пробует по очереди. Уже есть половина решения — вставка сырого `vless://` в v1.0.11.
3. **Раздать конфиги вне сети** (на случай факта 8, блока VLESS-хоста): base64-текст в мессенджере /
   one-time ссылка — механизм `.once` в fdge уже есть.

### Приоритет 2 — среднее
4. **Добавить Hysteria2 (QUIC/UDP)** как ещё один транспорт — камуфляж под HTTP/3, обходит TCP-фризинг.
5. **Снизить число параллельных TLS к одному SNI** (факт 4/9): включить mux в VLESS, чтобы не палиться
   на «>3 хендшейка к одному SNI».
6. **Ротация портов/поддоменов** с низким TTL (факт 3) — упреждающе, до блока.

### Приоритет 3 — если ДЦ-репутация OVH станет нерабочей
7. **Сменить/добавить хостинг с «чистой» репутацией** (не из списка факта 1: OVH/Oracle/CF/Hetzner/DO/AWS)
   — резидентный/локальный CDN-фронт, чтобы происхождение не читалось как «иностранный ДЦ».
8. **XHTTP-транспорт** вместо/вместе с WS — если подтвердится устойчивость (сейчас в «не проверено»).

**Философия (факты 2 и 6):** держать 3+ транспорта с авто-failover в клиенте и быстро крутить
инфраструктуру. Один протокол = одна точка отказа.
